# Как добавить алгоритм сжатия чанков (v2)

Этот документ описывает, как добавить новый алгоритм хранения чанков в
бенчмарк. Он используется в двух режимах:

- **Генерация одного файла** (в т.ч. LLM-агентом без доступа к проекту):
  прочитайте **только Часть I** — она самодостаточна. Вы пишете текст одного
  файла, сборку и запуск тестов выполняет пользователь.
- **Агент, работающий в проекте**: Часть I + **Часть II** — где что лежит,
  как проверять и что делать с результатом.

---

# Часть I — контракт алгоритма

## 1. Что требуется

Создать **один файл** `src/codec/sandbox/<name>.rs` (имя файла — по
алгоритму, латиницей). Файл реализует трейт `Codec` для нового формата
сжатия чанков и сам себя регистрирует через `pub const REGISTRY`.

Ничего в других файлах менять не нужно: `build.rs` сканирует каталог
`src/codec/` рекурсивно и автоматически объявляет модуль и добавляет его
`REGISTRY` в общий реестр. Регистрация в `src/codec/mod.rs` не требуется
вообще.

## 2. Разрешённые зависимости

Внутри файла можно использовать только:

- стандартную библиотеку Rust (`std`);
- крейт `anyhow` (`anyhow::Result`, `anyhow::bail!`, `anyhow::anyhow!`);
- крейт `flate2` (только если алгоритму нужно zlib/deflate-сжатие);
- типы, определённые в разделе 3–5 этого документа (реально они импортируются
  из `crate::chunk` и `crate::codec`).

Запрещено добавлять какие-либо другие крейты/зависимости, изменять
`Cargo.toml` или другие файлы проекта.

## 3. Типы данных

```rust
pub const CHUNK_W: usize = 16;
pub const SECTION_BLOCKS: usize = 4096;  // 16*16*16
pub const SECTION_BIOMES: usize = 64;    // 4*4*4

pub struct Section {
    pub blocks: Vec<u32>,   // ровно 4096 элементов; глобальные id блоков
    pub biomes: Vec<u16>,   // ровно 64 элемента; глобальные id биомов
}

pub struct Chunk {
    pub x: i32,
    pub z: i32,
    pub section_min_y: i32,     // мировая y первой секции
    pub sections: Vec<Section>, // по порядку: y = section_min_y + k*16
}
```

Индексация: для секции `si`, локальной высоты `ly` (0..16), `z` (0..16),
`x` (0..16) индекс в `blocks` равен `ly * 256 + z * 16 + x` (как в
`Chunk::block_at`).

- `blocks` хранят глобальные id блоков; `id == 0` всегда «air».
- `biomes` — глобальные id биомов.
- Пустая секция (всё air) — нормальный случай, обрабатывайте его.
- Реальные чанки 1.18+ имеют 24 секции (`section_min_y = -64`); легаси-миры —
  другое число секций и другой `min_y`. Не полагайтесь на фиксированную
  высоту.

## 4. Контекст

```rust
pub struct Ctx<'a> {
    pub registry: &'a BlockRegistry,
    pub biomes: &'a BiomeRegistry,
    pub biome_block_lists: &'a [Vec<u32>], // на биом: до 255 блоков (глобальные id)
}

pub struct BlockRegistry { pub names: Vec<String> } // get(name) -> Option<u32>
pub struct BiomeRegistry { pub names: Vec<String> } // get(name) -> Option<u16>
```

Использование:

- `ctx.registry.names[id]` — имя блока (состояния) по глобальному id;
- `ctx.registry.get("имя")` — id по имени (`Option<u32>`);
- `ctx.biomes.names[id]`, `ctx.biomes.get("имя")` — аналогично для биомов;
- `ctx.biome_block_lists[biome_id]` — список характерных для биома блоков
  (глобальные id, отсортированы по частоте).

Правила:

- `get()` только читает. Мутировать `Ctx` (и реестры внутри него) **запрещено**.
  Метода `intern` у кодека нет — реестр доступен только по ссылке `&`.
- В `decode_tile` используйте только `get()`, никогда не подменяйте
  неизвестные имена нулями «наугад» — round-trip обязан совпадать.

## 5. Трейт

```rust
pub trait Codec: Send + Sync {
    fn group_size(&self) -> usize { 1 }

    fn encode_tile(&self, chunks: &[&Chunk], ctx: &Ctx) -> Vec<u8>;
    fn decode_tile(&self, bytes: &[u8], ctx: &Ctx) -> Result<Vec<Chunk>>;

    // convenience для group_size == 1 — реализовывать не нужно:
    // fn encode(&self, chunk: &Chunk, ctx: &Ctx) -> Vec<u8>;
    // fn decode(&self, bytes: &[u8], ctx: &Ctx) -> Result<Chunk>;
}
```

(`Result` — `anyhow::Result`.)

- Вся текстовая мета (`id`, `name`, `group`, `description`) живёт **только в
  `REGISTRY`** (раздел 7) — в трейте её нет.
- `group_size()`: `1` (по умолчанию) — один чанк за вызов. Можно вернуть `4`,
  тогда тайл — квадрат 2×2 чанка, `chunks` имеет длину 4; `decode_tile`
  обязан вернуть столько же чанков. Все чанки одного тайла имеют одинаковый
  размер и высоту.

## 6. Правила контракта

1. **Round-trip обязателен**: `decode_tile(encode_tile([chunk]))` должен
   вернуть вектор чанков, идентичных исходным: те же `sections` (длина и
   содержимое `blocks` и `biomes`) и тот же `section_min_y`. `x`/`z` можно
   не сохранять. Это проверяется функцией `chunks_equal` в `src/bench.rs`.
2. Возвращаемая `Vec<u8>` — просто последовательность байт. **Префикс длины
   писать нельзя**: длину знает только вызывающий (фрейминг). Если декодеру
   нужна размерность (число секций, `section_min_y`), запишите её в поток
   сами (как это делают `minecraft` и `layered`).
3. Один формат — один поток: порядок байт/бит внутри потока детерминирован
   и полностью восстановим. `encode`/`decode` строго симметричны.
4. `decode_tile` не должен читать ничего вне `bytes` и не должен мутировать
   `ctx`. Лишние/недочитанные байты в конце — ошибка (сравните: в примере
   `template.rs` стоит проверка `p != bytes.len()` → `bail!`).
5. Никакого глобального состояния, `unsafe`, многопоточности.
6. Не храните `Vec<u8>`-длину в потоке — только если это реально часть
   формата (varint-поля внутри потока допустимы).
7. Если нужны битовые поля/varint — в `src/codec/base/layered.rs` есть
   готовые `BitWriter`/`BitReader` (LSB-first); можно позаимствовать или
   написать свои.

## 7. Регистрация

В конце файла (или рядом с `impl Codec`) обязательно объявите:

```rust
use crate::codec::RegistryEntry;

pub const REGISTRY: &[RegistryEntry] = &[RegistryEntry {
    id: "my-algo",  // уникальный короткий id (латиница, дефисы/цифры)
    name: "My Algo (palette + RLE)", // человекочитаемое имя
    group: "palette-rle",
    description: "1-2 предложения: как работает и для каких данных хорош.",
    make: || Box::new(MyAlgoCodec) as Box<dyn Codec>,
}];
```

Поля `RegistryEntry`:

- `id` — уникальный короткий идентификатор, попадает в JSON-отчёт.
- `name` — человекочитаемое имя, видно в отчёте и на графиках.
- `group` — категория для раскраски графиков, отражающая механизм сжатия.
  Существующие группы: `"raw"` (без сжатия), `"rle"` (run-length),
  `"layered"` (слои), `"minecraft"` (стандарт MC), `"palette"` (палитра +
  битпак), `"palette-rle"` (палитра + RLE), `"adaptive"` (выбор наименьшего
  представления на секцию), `"context-modeling"` (контекстное моделирование +
  арифметический кодер), `"predictive"` (пространственный предиктор),
  `"deflate"` (zlib/deflate). Если вашего метода нет среди существующих —
  укажите свою строку; группа влияет только на цвет на графиках.
- `description` — 1–2 предложения, попадает в отчёт и на страницу.
- `make` — фабрика: возвращает `Box<dyn Codec>`.

Это вся мета: ничего из неё в `impl Codec` дублировать не нужно — методов
`id()`/`name()`/`description()` в трейте нет.

Если у алгоритма есть параметры, добавьте **несколько записей** в массив
`REGISTRY` — по одной на набор параметров (у каждой — свои `id`/`name`).

## 9. Валидность и частые причины провала

Алгоритм валиден, если проект собирается (`cargo build --release`) и в выводе

```bash
cargo run --release --bin mc-chunk-bench -- bench --max-chunks 512
```

его `id` присутствует с `ok=true` (round-trip прошёл). Остальное (сборка,
запуск, анализ) делает пользователь.

| Проблема | Решение |
|---|---|
| `decode` даёт не те блоки | Проверьте порядок байт/бит; поток должен читаться ровно до конца (лишние/недочитанные биты). Сравните свой поток с `layered`/`minecraft`. |
| Всё декодируется в 0 | В `minecraft`-подобных форматах упаковывайте **индексы палитры**, а не глобальные id. |
| Биомы не совпадают | `biomes` — часть round-trip. Либо храните их в потоке, либо копируйте из исходника (не подменяйте нулями). |
| Поток читается не до конца / есть лишние байты | Нарушение п. 2/4: префикс длины, несимметричный encode/decode. |
| Медленный encode | Избегайте аллокаций на каждый блок; пишите в `Vec<u8>` с `with_capacity`; не используйте `format!` в горячем цикле. |
| Запрещённые зависимости или мутация реестра | Только `std`/`anyhow`/`flate2`; в decode — только `get()`. |

# Часть II — для агента, работающего в проекте

## 10. Где что лежит

| Место | Что там |
|---|---|
| `src/codec/sandbox/` | песочница: **новые** реализации. Файл с `REGISTRY` автоматически попадает в бенчмарк. Подробнее — `src/codec/sandbox/README.md`. |
| `src/codec/sandbox/template.rs` | рабочий минимальный образец кодека; скопируйте как отправную точку. |
| `src/codec/base/` | эталонные алгоритмы (не редактировать ради экспериментов): `raw.rs` (эталон скорости), `rle.rs`/`rle-linear` (простой RLE), `minecraft.rs` (стандарт MC: палитра + бит-упакованные longs, varint'ы, строки с префиксом длины), `layered.rs` (`BitWriter`/`BitReader`, составные заголовки, выбор наилучшего представления). |
| `src/codec/custom/` | принятые кастомные кодеки — примеры более продвинутых техник (палитры, контекстное моделирование). |
| `src/codec/disabled/` | отключённые кодеки (`REGISTRY` закомментирован), сохранены для справки. |
| `src/codec/mod.rs` | трейт `Codec`, `Ctx`, `RegistryEntry`. **Не изменять.** |
| `src/codec/deflate.rs` | обёртка, добавляющая zlib к любому кодеку (тумблер «Сжатие» в веб-UI даёт варианты `<id>+deflate12`). |
| `src/chunk.rs` | модель чанка, `Chunk::block_at`, константы `SECTION_BLOCKS`/`SECTION_BIOMES`. |

## 11. Как проверять

Три уровня проверки + полный бенчмарк:

1. **Unit-тесты** (`cargo test`) — свои тесты пишите в `#[cfg(test)]`
   внутри файла кодека.
2. **Синтетический round-trip** (`cargo run --release --bin laytest`) —
   гоняет `layered` по паттернам (равномерный, шумный, колонки, серии).
   Для своего алгоритма добавьте аналогичную проверку (можно вынести общий
   хелпер синтетического чанка).
3. **Реальные чанки из миров** (`cargo run --release --bin dbg`) — читает
   настоящие сейвы (путь по умолчанию `~/.minecraft/saves`, можно передать
   первым аргументом). Подключите свой алгоритм так же, как там проверяются
   `minecraft` и `layered`.
4. **Полный бенчмарк** (самый важный тест):
   ```bash
   cargo run --release --bin mc-chunk-bench -- bench --max-chunks 512
   ```
   Замеряет encode/decode, размер и проверяет round-trip для всех
   алгоритмов из реестра. Если `ok=false` — в отчёте будет причина
   (decode-ошибка или несовпадение данных). Затем `serve`:
   ```bash
   cargo run --release --bin mc-chunk-bench -- serve --port 8085
   ```
   Новый алгоритм автоматически появится на графиках и в таблице.

## 12. Чек-лист агента

- [ ] Создан `src/codec/sandbox/<name>.rs` с `impl Codec`.
- [ ] В этом же файле объявлен `pub const REGISTRY: &[RegistryEntry]`
      (категория, описание, фабрика).
- [ ] `src/codec/mod.rs` **не изменялся**.
- [ ] `cargo build --release` собирается без ошибок (build.rs сам подхватил файл).
- [ ] `cargo test` проходит.
- [ ] `bench --max-chunks 512` показывает `ok=true` для нового алгоритма
      и его `id` в списке.
- [ ] `serve` — алгоритм виден на странице.

## 13. Жизненный цикл алгоритма

- **Удался** → переместите из песочницы в принятые:
  `git mv src/codec/sandbox/my_algo.rs src/codec/custom/my_algo.rs`.
- **Не удался** → удалите файл. Можно оставить на время, закомментировав
  `REGISTRY` (код сохранится, но в бенчмарк не попадёт).

Правила песочницы (подробнее — `src/codec/sandbox/README.md`):

- один файл — один алгоритм (или один набор вариантов одного алгоритма);
- не редактируйте кодеки из `base/` и `custom/` ради экспериментов;
- медленный, но плотный алгоритм — это нормально, ему есть место в `custom/`.
